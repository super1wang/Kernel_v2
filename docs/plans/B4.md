## 执行步骤与高风险前置

1. 先建立接收后可能 inline、拒绝却迟到调用、重复执行/完成、worker 自等待/自关闭、stop 超时及资源半获失败反例。冻结端口寿命选择，必要重大决策记录 ADR；不重审 Passed 历史证据。
2. 实现生产 BS::thread_pool 适配；第三方池只接收已就绪 work，不拥有业务 Task。业务侧 ExecutorPort 仍只有 submit；owning controller 的可选 ExecutorControlPort 负责 in_worker/drain_until/shutdown_until/最终回收，Scheduler 只取得窄 submit port。超时不销毁池、不 detach，owner 继续持有依赖直到真实排空。可控/inline 后端用于同版本端口验收，不登记故障后端为合格。
3. Scheduler 在 mutex 内将 Ready 转为 Dispatching{attempt_generation} 并登记投递预算，然后解锁；**ExecutorPort::submit 本身与业务、completion 均为锁外可重入边界**。inline completion 允许在 submit 返回前完成内部迁移；返回后不得假设仍在 Dispatching。Rejected/exception 只处理仍有效的 attempt；inline 已完成时只记录后端违约，不反向回滚、不重通知、不重复释放。迟到/重复 execute 由 attempt token 检测。Dependency set 在 scheduler entry 发布时冻结；首版只允许引用已发布 predecessor，self、duplicate、unknown predecessor 均拒绝。dependent attach 与 predecessor completion 使用同一 Scheduler 仲裁：已完成 predecessor 不增加 unresolved_count，未完成则先登记 adjacency 再计数；completion 只 drain 一次 adjacency，迟到/重复完成不得造成计数下溢或丢 wake。
4. **Started 的唯一判据是 ReadyWork envelope 在进入业务前，以当前 attempt_generation 成功取得 start claim。** start claim 与 deadline expiration 在同一 Scheduler 仲裁边界竞争；Start 先赢才允许业务进入，deadline 先赢则该 execute 必须无业务副作用并仅完成 envelope 收尾。submit 接受、worker dequeue 或进入 execute 函数本身均不等于 Started。deadline 对尚未 Started 的 Ready、dependency 与 resource waiter 精确摘除一次，使原 attempt/wait generation 失效；迟到 timer/wake 不得重新排 Ready。已投递但尚未 execute 的 work 也不得开始业务，worker_delivery reservation 与投递 ReadyWork envelope 寿命绑定：符合端口合同的 Rejected/exception 返回（已交还/销毁 envelope），或 accepted envelope 最终收尾时，reservation 精确释放一次。若违约后端在拒绝/异常后仍持有 envelope，只作逻辑拒绝并使 attempt 失效，物理 reservation 保留到真实收尾，不能虚减实际 delivery。已 Started 不强制中止，由 B5 承接协作期限。本层仅报告内部 ExpiredBeforeDispatch/ExecutorRejected 等事实，不制造 CancelledBeforeApply、FailedBeforeApply 或 Execution Terminal。
5. 冻结资源拓扑及别名归一、MultiClaim 全获/零占用与移动 Lease。release 在资源锁内更新容量、标记 waiter generation、摘除该 waiter 的全部索引并生成一次 wake token，**锁外**通知 Scheduler；Scheduler 也不持锁调用 ResourceManager。wake 仅提示重新 normalize/aggregate 并原子尝试全部 claims，不代表获得/保留资源；失败后以新 generation 挂回所需索引。取消/过期与多线程释放竞争不得重复 requeue、双释放或留下 waiter。提交专属资源不能在计算阶段持有；父子等待前必须释放重叠资源，否则拒绝组合。
6. Debug fail-fast 直接影响集开发；稳定后集中 SPEC/CODE 与同来源 Debug/Release/ASan 正式影响集。各后端公共必需项不能 skip；能力可选项为有合同理由的 NotApplicable，不计 Passed。真实线程专项不由确定性测试或 ASan 替代。

## 集成、预算与证据

- 构建形态冻结为累计开发 **B4Subset = B3Subset + 生产 Adapter::CpuPool**，依赖 acquisition 为 CLI + CpuPool；Scheduler/Resources 编入 OCK::Runtime。Runtime-only 仍仅取得 expected，不取得 thread_pool。CpuPool 只 PUBLIC 依赖 CoreContracts，BS 仅私有编译头；B3Subset 保持原组件选择。B4 的实际安装消费者及 Runtime-only 裁剪分别证明该边界，B4Subset 不宣称完整 Embedded/G3。初版临时 OCK_BUILD_CPU_POOL 开关应收敛到明确 Profile，而非形成未审查组合。
- 分别记账 principal_queued、principal_inflight、global_queued、global_inflight 和 worker_delivery；主体 queued 256、全局 queued 4096，inflight 与 delivery 由可信配置独立限额。主体按权重轮转，priority 仅影响主体内部有限份额；持续 Runnable 的合法主体不得被另一主体持续高优先级提交永久饿死。依赖/资源阻塞者不参与公平计数。测试记录调度顺序、计数和有界等待轮次，不能只测平均吞吐。
- 待通知完成仍占用有界 entry 容量（global_queued + max_inflight）；外部完成回调阻塞时不能无限积累 captures。已摘索引而待唤醒的 resource waiter 仍计入 waiter 预算，至通知开始才归还容量。
- 控制保留 128 仅建立独立容量/接口缝，不新增 execution.cancel 或第二控制任务系统。history 仅为 scheduler-local minimal completion/dependency metadata，不是 Execution terminal history；ExecutionRef/get/list 仍属 D3.04。
- 首版明确 resource_factory capability=absent，普通未知 ResourceKey 全拒绝；架构仍允许以后由已注册 factory 在 namespace/capacity/topology policy 下创建有界 slot，用户任意字符串永远不能直接创建。拓扑/别名/claims/waiter 数量均有界，预算失败不能静默丢弃。
- D3.01 交付版本化 conformance_manifest，至少包含 port_contract_version、backend identity/source digest、capabilities、applicable cases 与 fixtures；各工厂复用同一共同预期，故障后端资格与消费者检测结果分开。
- 验证覆盖共同合同、真实线程/并发释放、满载/主体配额、依赖/deadline、inline/故障 Executor 防御、资源溢出/别名/部分失败/父子等待与 scheduler 集成；保存公平与历史规模原始样本，不能用更多历史使每轮 pump 线性变慢。
- 新公开头独立安装消费、组件裁剪与 SDK manifest 同步纳入实际变更影响。正式 expected 在发现/执行前从完成条件固定；复用现有 E03 与 AI 自动验收，不扩展证据工具或重跑 G1/B2/B3 累计矩阵。
- 正式配置结果与 review 输入绑定同一已提交来源，失败原始证据不覆盖。必要实现提交及最终归档提交用英文 B4 标识，并推送当前任务分支，不强推。结束前逐条核对本表与包卡交付，未完成项不得改名为 deferred 后宣布 B4 完成。

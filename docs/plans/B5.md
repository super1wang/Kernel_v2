## ResourceWaitBinding 无丢唤醒协议（B5 必须实现）

1. 先准备拥有型 Execution entry、binding owner 与完成/摘除回调，再发布 resource_ready=false 的 Scheduler entry 并取得稳定 ticket；仅发布成功后才调用 acquire。enqueue 失败不申请资源，不发布 Accepted。Scheduler completion 可能早于 enqueue 返回，因此预建 binding 必须能先记 terminal，ticket 发布后发现 terminal 则不 acquire。ExecutionRef 的接受边界仍遵循 D3.04；Scheduler ticket 不能替代 ExecutionRef。
2. Binding 归 Runtime Execution owner，包含 ticket、单调 attempt_generation、阶段 Installing/Waiting/Retrying/Ready/Terminal、wake_pending、ResourceManager waiter_generation、owning waiter 与 optional lease。binding generation 与资源 generation 是不同字段，不能混用。每次 acquire 前在同一 binding 仲裁锁下预留新 attempt，再解锁 acquire；不持 Scheduler/binding 锁调用 ResourceManager，不持资源锁调用 Scheduler。
3. wake 可早于 acquire 返回和 waiter 安装。wake 捕获 owning binding 与当前 attempt，仅在该 attempt 活跃时登记 wake_pending 和收到的资源 generation；Installing 阶段只记账，不递归 acquire。acquire 返回在同一仲裁锁安装 waiter 并核对资源 generation；已 pending 则摘下旧 waiter，转换到唯一 Retrying，锁外取消后重试全部 claims。等待/重试均只有一个驱动者；每次失败挂回使用新的 attempt 和资源 generation。
4. cancel/deadline/terminal 与 acquire 返回、wake、lease 安装使用同一 binding 仲裁；终止先使 generation 失效，再移出 waiter/lease，锁外销毁。acquire 在途时允许先标 terminal，但其 owner 必须存活到返回；返回的 waiter/lease 若失效立即锁外取消/释放，不安装、不 make_ready、不进入业务。wake 与 terminal 竞争由相同仲裁决定，旧 generation 不能唤醒新 attempt。
5. 获得 lease 后先在 binding 中安装，进入 Ready，然后锁外 make_ready(ticket)。业务读取 lease 必须通过同一有效 binding；make_ready 失败要在仲裁下移出仍属于该 attempt 的 lease，再锁外释放。调用期间 terminal 可先摘掉 lease，返回路径不得重复释放。deadline/start claim 的最终开始判据继续由 Scheduler 仲裁；已 Started 的取消为协作，不能提前释放业务仍使用的 lease。
6. wake 只提示重新申请全部 claims，不能直接判为持有资源。终态、重试与失败收尾精确摘除 waiter；失效 callback 持有的 owner 到实际回调/capture 收尾才释放。内部可靠完成与外部可丢通知分离；不使用丢 wake 或无限轮询补偿错误顺序。

必测交错：wake 早于安装/晚于安装；deadline/cancel 在 acquire 前、在途及返回安装前；wake 与 terminal 同时；旧 wake 晚于新 waiter 安装；make_ready 失败；inline completion；重复 wake；关闭时 capture 析构重入；每种终止后资源 used/index/waiter 与投递额度归零。使用受控屏障和真实线程，不能只靠 sleep。

## 0. 执行摘要

B6 的核心收口已经有效完成。上一轮审计中要求关闭的 C1–C6 已经真实进入生产路径：State 的取消/关闭与提交许可已通过 `CommitClaim` 进入统一仲裁；每次提交携带独立 PublicationProof；Snapshot 在同一锁内捕获版本与生命周期身份；prepared 采用精确 owner/弱 reservation；Atomic 已从冻结 Registry 绑定真实业务函数、类型、provider、targets 和 resources；History 支持字节压力回收并对 retained owner 与索引节点进行独立计量；公开 Host 已覆盖真实 StateEdit/Atomic Submit/Wait/Result/Stop。

仓库正式记录显示 B6 closure 的 Debug/Release/ASan 三配置均为 **89/89 Passed**，并完成 StateNative 9/9、Runtime-only 安装、Native/Embedded 原预算复核和 18 组 N×k×引用状态成本样本。历史 B6 Passed 不需要撤销。

本轮复审仍发现 **2 项 P2 级合同残留**。它们不会推翻 B6 的既有 Passed 事实，但属于 B6 在最终冻结前应补齐的边界语义：

1. **Atomic 组显式 revision 前置尚未在注册层强制。** 当前组注册仍可采用 `ServerCapture`，与 A07.1“对外 Atomic 必须具有精确 revision 前置条件”的规则不一致。
2. **State 失败结果事实仍不够精确。** 取消先赢时可能被映射成 `FailedBeforeApply/NotReached`，而不是 `CancelledBeforeApply/CancelWon`；同时 `business_entered` 在进入 State thunk 前即被视为 true，导致显式 revision 失败等“业务未进入”路径仍可能被记录为业务已进入。

因此本文件仅定义 **B6 的最终优化与精确化收口**：

```text
B6 / D4.01–D4.04              Passed（历史事实保留）
B6 audit closure C1–C6        Passed
B6 final precision P2-A/P2-B  Required
```

这两项修复应合并为一个窄的 **B6 post-closure 精确化补丁**，不建立新的大阶段、不重跑 B1–B5 全矩阵，也不重新设计 State/Atomic。

## 2. 路线复核：哪些已经正确，哪些不能再改回去

### 2.1 不存在整体路线偏移

当前仍遵守原架构的几个关键原则：

- Runtime 不反向依赖 State；State 公开只依赖 CoreContracts。
- State 的 immer 保持私有实现，不进入安装公共头。
- 单条 StateEdit 与 Atomic 复用同一注册业务函数，不建立第二套 Handler。
- Atomic 使用冻结 Registry 的真实 Operation、类型、provider、targets 和 resources，不依赖客户端自行描述裸函数。
- Published 后的状态事实不会因为结果编码、观察或迟到取消而回退成“未应用”。
- Native、managed、Atomic 都继续走同一 Policy / Permit / Publication gate。

这些边界应当作为 B6 最终冻结后的硬合同；任何上层调用方只能消费这些能力，不能在外围重新发明 State 提交协议。

### 2.2 本次 B6 优化中禁止的“补丁式修复”

以下做法全部应禁止：

- 在上层外围判断 revision，而底层 Atomic 仍允许 `ServerCapture`。
- 在调用方根据错误码猜测 Cancelled/Failed，而 Runtime Outcome 事实仍错误。
- 引入第二套 StateEdit/Atomic 执行器来规避现有合同问题。
- 将 Atomic 拆成多个普通 StateEdit 再声称“原子”。
- 为方便调用缓存动态权限结果、Caller 或 ActionPermit。
- 用外围状态覆盖底层真实 Commit/Publication 事实。

## 3. 上轮 C1–C6 收口复核

### 3.1 C1：取消/关闭与真实提交仲裁 —— 核心机制已关闭

当前 `StateDomain::commit()` 不再把进入 `Claiming` 视为已经赢得提交。真正的线性化点是 `PermitAuthorityPort::consume_claimed(..., CommitClaim&)`：Policy 在自身仲裁锁内重新验证权限、期限、撤权和 permit，然后最后执行 claim；`close()` 只可以取消尚未 claim 的提交。

Runtime 还会在 State 业务执行前安装 owning stop callback，将请求取消接到当前 `ActionAuthorization::cancel()`。这已经关闭“业务开始后请求取消但仍可照常 publish”的上一轮 P1。

### 3.2 C2：逐提交完成材料 —— 已关闭

`CommitReport` 已携带本次提交自己的 PublicationProof；Runtime 对完整 PreparedIdentity 和 disposition 进行核对后，直接使用本次 proof 封口结果，不再依赖 provider 的“latest published”槽。

直接回归已经构造 C1 先 publish、C1 返回被延迟、C2 publish 并完成、C1 再封口的并发交错，说明上轮“第二次发布覆盖第一次证明”的问题已经被实质解决。

### 3.3 C3：生命周期 identity 与 prepared owner —— 已关闭

Snapshot 现在在同一 StateDomain 锁内同时捕获 `PublishedState` 与 lifecycle identity，避免旧状态与新 identity 拼接。prepared 的唯一 reservation 由实际 owner 表示，provider/frame 持有本次 prepared owner；失败和 abandon 只释放精确匹配项，不再由 domain 永久强持有一个失败候选。

### 3.4 C4：Atomic 同源治理 —— 主体已关闭

新增 `CandidateBindings` 从冻结 Catalog 中绑定真实：

- operation + contract digest；
- Args/R 类型；
- handler；
- provider owner；
- target projection；
- resource declarations；
- candidate read / pure compute / state edit 模式。

每一步执行前会重新验证输入 TypeContract 和 target projection；组内每一步通过 `CandidateAuthorizationPort` 重验当前 Action；完整资源集合由真实 Host ResourceManager 一次性获取。公开 Host 测试已经覆盖非空 Exclusive 资源、第二组等待、前序值改变后一步 target、第一步后撤权等反例。

剩余的**唯一治理缺口**是组级 revision policy 还没有被强制为精确前置，详见 P2-A。

### 3.5 C5：History 压力回收与计费 —— 正确性缺口已关闭

History 不再只有“覆盖同一 ring slot 时才释放”的策略。当前 `reserve_history()` 会在字节压力下有限扫描并淘汰无外部 owner 的最老记录；被 HistoryView / prepared 等持有的记录继续占用 retained charge，直到最后 owner 析构。

ObjectRoot 还使用私有 immer allocator policy 对索引节点执行实际分配计量和上限约束，逻辑正文 bytes 不再冒充完整索引堆占用。

### 3.6 C6：真实公开消费者与成本 —— 已明显补强

当前回归已覆盖：

- 公开 Host + CpuPool StateEdit submit/wait/result；
- Atomic submit/wait/result；
- RequireExplicitRevision 正反例；
- 非空资源冲突；
- necessary record 故障和 Finalizing 排空；
- StateNative 迁移安装；
- Runtime-only 裁剪；
- Native / Embedded 原预算；
- N={1k,10k,100k} × k={1,10,100} × 有/无引用 18 组成本组合。

因此这次不需要再将 B6 判回“未实现”，剩余工作属于精确合同收口。

## 4. P2-A：Atomic 组必须强制精确 revision 前置

### 4.1 当前问题

现行 A07.1 的语义是：

- **单条 StateEdit**：可以由可信注册者声明 `ServerCapture` 或 `RequireExplicitRevision`。
- **对外 Atomic**：绑定完成后必须具备精确 revision 前置条件。

目前 `atomic::register_group()` 将调用方传入的普通 `OperationOptions` 原样交给 `registrar.state_edit()`；Registry 只是验证 `revision_policy` 是合法枚举，没有强制 Atomic 组使用 `RequireExplicitRevision`。

因此当前仍然存在合法的以下注册：

```text
Atomic group operation
revision_policy = ServerCapture
```

并且当前直接测试确实执行过“没有 expected_state 的 Atomic invoke 并成功提交”。这说明问题不仅是理论上的“有人可能误配”，而是现有合同没有锁死。

### 4.2 风险

对脚本、自动化和高层业务调用来说，Atomic 的主要语义价值之一就是：

> “基于我检查过的这个状态版本，把这组相关修改作为一次原子提交。”

若允许 ServerCapture，则以下序列不会失败：

```text
调用方检查时看到 revision=10
        ↓
其他执行提交 revision=11
        ↓
Atomic 执行时自动捕获 revision=11
        ↓
组仍然运行
```

这会把“精确前置失效”静默变成“在另一个状态版本上重新解释同一组操作”。对 CAD/CAM/工业控制业务而言，这是高风险的语义漂移。

### 4.3 推荐修复

采用 **fail-closed**，不要依靠调用方自律。

推荐两种等价实现，优先 A：

**方案 A（推荐）：`register_group()` 强制要求 `RequireExplicitRevision`**

```text
register_group(..., options)
    if options.revision_policy != RequireExplicitRevision:
        reject InvalidDefinition/InvalidContract
```

优点：

- 语义最清楚；
- 不会在 helper 内静默重写调用者配置；
- Registry 冻结结果可以直接审计；
- 后续任何调用方都不需要知道“某些 Atomic 可以 ServerCapture”的例外。

**方案 B：专用组注册 API 内固定 canonical policy**

如果希望调用端减少配置，可由专用 Atomic 注册 API 直接构造 `RequireExplicitRevision`，同时不允许外部覆盖。

不建议“如果调用者传 ServerCapture 就自动改掉且不报错”，因为这会掩盖注册错误。

### 4.4 必补反例

最少增加以下 6 条：

1. Atomic group 注册为 ServerCapture → 注册失败。
2. 缺 `expected_state` → 业务步骤 0 次进入，permit 0 次消费，revision 不变。
3. stale revision → 业务步骤 0 次进入，revision 不变。
4. stale lifecycle generation → 业务步骤 0 次进入。
5. 精确 revision 匹配 → 正常一次 commit。
6. 两组同一 base 并发 → 至多一个成功；第二个明确 revision conflict，不自动重算。

Native invoke 和 Host submit 至少各覆盖一条缺失/过期前置。

## 5. P2-B：State 失败 Outcome 必须准确表达业务进入与取消仲裁

### 5.1 当前正确的部分

提交本身已经安全：

- 取消先赢可以阻止 `consume_claimed()`；
- 撤权、期限、关闭可以在 claim 前阻止发布；
- claim 后不会被迟到取消抹掉 `StateCommitted`。

剩余问题是 **Outcome 记录事实没有完全跟上底层仲裁**。

### 5.2 当前两个不准确点

#### 问题一：CancelWon 被折叠成 FailedBeforeApply / NotReached

State thunk 的 commit 失败最终进入 `call.failure`；外层 `NativeBound::run()` 对任何 `call.failure` 都调用通用：

```text
outcome_failure(error, facts, entered=true, accepted=managed)
```

没有传入 `cancelled=true`。

所以即使实际是：

```text
stop callback → ActionAuthorization::cancel()
consume_claimed → PolicyErrc::Cancelled
```

最终仍可能得到：

```text
FailedBeforeApply
ApplyDecision::NotReached
```

而不是架构要求的：

```text
CancelledBeforeApply
ApplyDecision::CancelWon
```

#### 问题二：业务尚未进入也可能被写成 business_entered=true

外层当前在调用 `NativeAccess::dispatch()` 前就把 `entered=true`。

但 State thunk 内部还会先执行：

- provider begin；
- base 获取；
- explicit revision / lifecycle 校验；
- provider 合同检查；

之后才真正调用业务 handler。

所以显式 revision 过期这类路径中，业务函数根本没有进入，但 Outcome 仍可能被标记成 business_entered=true。

### 5.3 为什么必须在 B6 最终冻结前修

如果底层 State 自身的“是否进入业务”“取消是否先赢”是模糊的，那么任何 Native、Submit、CLI 或未来组合调用都只能根据错误码或外部状态进行二次猜测，这会造成：

- 上层复制底层仲裁逻辑；
- Native 与 managed Submit 的结果事实不一致；
- 迟到取消更容易误覆盖已经发生的提交；
- 观察、诊断和自动化逻辑无法稳定依赖 Outcome。

因此必须在 B6 最终冻结前，让 **最底层产生事实的一层** 正确表达结果。

### 5.4 推荐的数据流

不要仅在外层根据最终 `stop_requested()` 猜取消，因为迟到 stop 可能发生在 claim 后。

建议让 State 调用适配显式返回受信事实：

```text
StateCallFacts
    business_entered: bool
    commit_decision:
        NotReached
        CancelWon
        ClaimWon
    committed: bool
    failure/error
```

其中：

- `business_entered` 只在真正准备调用业务 handler 前置为 true；
- `CancelWon` 只来源于实际提交仲裁，而不是“结束时 stop_token=true”；
- `ClaimWon + Published` 形成 StateCommitted；
- `ClaimWon` 后若发生可信内部故障，按真实 KnownNotCommitted / Indeterminate 规则处理，不能伪造 CancelledBeforeApply。

实现上不要求引入一个重量级公开类型。可以：

- 扩展私有 `StateNativeCall`；或
- 给 `CommitReport` 增加足够的 BeforeApply/decision 材料；或
- 增加一个 CoreContracts 窄 DTO，只携带事实，不授予能力。

核心要求是：**完成器消费明确事实，不从 ErrorCode 反推完整时序。**

### 5.5 正确结果矩阵

| 实际事实 | 正确结果 |
|---|---|
| 接受前参数/绑定失败 | `Rejected` |
| 已 Accepted，但 explicit revision 在业务前失败 | `FailedBeforeApply`，`execution_accepted=true`，`business_entered=false` |
| Handler 已进入，普通准备失败，确认未应用 | `FailedBeforeApply`，`business_entered=true` |
| 取消先赢，确认未应用 | `CancelledBeforeApply`，`CancelWon` |
| 撤权/期限先赢，确认未应用 | `FailedBeforeApply` 或规范对应失败，不能谎称 CancelWon |
| claim/publish 成功后 stop 到达 | 保持 `StateCommitted` |

### 5.6 必补反例

至少补以下 8 条：

1. Native StateEdit：业务返回前 request_stop，取消先赢 → `CancelledBeforeApply/CancelWon`。
2. Host submit：Running 后 cancel，claim 前赢 → 同上且保留 ExecutionRef。
3. claim 后 request_stop → `StateCommitted` 不被覆盖。
4. explicit revision stale → `business_entered=false`。
5. lifecycle stale → `business_entered=false`。
6. Handler 返回业务错误 → `business_entered=true`、FailedBeforeApply。
7. permit revoke/expiry → 不误报 CancelWon。
8. managed result.read / execution.get 对同一 execution 输出一致事实。

## 8. 高收益、非阻塞优化

### O1：History 压力回收从重复全表扫描改为有界单轮扫描

当前 `reserve_history()` 在字节不足时：

1. 扫描整个 ring 找最老的、`use_count()==1` 的记录；
2. 淘汰一条；
3. 再从头扫描整个 ring；
4. 直到够用或无可淘汰项。

当 ring 容量为 H、一次需要回收多条时，最坏扫描工作量接近 O(H²)。由于 H 有配置上限，这不是无界算法，也不是正确性 blocker，但在较大 History 配置和大对象提交下会增加 commit prepare 尾延迟。

#### 推荐优化

优先采用**有界回收游标**，而不是引入后台 GC 或复杂 heap：

```text
reclaim_cursor
    ↓
一次最多扫描 H 个槽
    ↓
收集最多 reclaim_batch 个可淘汰 owner
    ↓
锁内拆索引
    ↓
锁外析构
```

要求：

- pin/外部 owner 仍不可删；
- 每次扫描仍受 `history_entries` / `reclaim_batch` 限制；
- 不改变 ring cursor / Undo/Redo 语义；
- 先采样再决定是否引入更复杂索引。

**优先级：P3 / 非阻塞优化。**

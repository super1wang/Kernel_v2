## 2. 组件边界、已有端口与 B5 接线

### 2.1 必须保持的生产 DAG

```text
Foundation
    └─ CoreContracts
         ├─ Runtime：Registry / Policy / Invocation / Execution
         ├─ State：Snapshot / Edit / History / Commit / Atomic
         └─ Adapter::CpuPool（需要受管理执行时装配）

settings_service（组合根）
    ├─ Runtime
    ├─ State
    └─ 可选 CpuPool
```

`OCK::State` 直接内部依赖仅为 `CoreContracts`；通用对象容器私有使用已锁定 immer。`Runtime` 不链接 State，State 不调用 Runtime 私有符号；双方通过 CoreContracts 的必要窄协议连接。需要同时知道 Runtime 和 State 的注册胶水放组合层，不把胶水藏成反向依赖。Snapshot、History、Atomic 是 State 内部目录，不各自新增公开 target。[S4]

已核对的接口包括 `EditView<P>`、`PreparedIdentity`、`PreparedCommit`、`AtomicProviderPort<P>`、`CommitReceiver/CommitReport`、`PublicationAuthorityPort`、`ActionPermit/PermitAuthorityPort`。它们提供合同起点，但不等于已有 State 实现。特别是当前 PreparedCommit 公开材料主要是身份与 receipt；不可假定它已经拥有候选 root、History 和最终业务 R。[S5]

### 2.2 本批实施决定：只补所需的类型化桥接

State 私有持有 `PreparedPublication` 一类的真实候选 owner，并将其与 provider/domain、CommitId、ReservationId、base revision、lifecycle generation 对应。公开 PreparedCommit 中的 DTO、receipt 或复制出的标识不能授予发布权限。候选必须来自当前受信 provider 的准备过程，commit 时核验实际 owner、类型与一次性状态；失败、取消和关闭都须拆除保活关系。

Runtime 的已有注册支持 StateEdit/CandidateRead 的描述，但当前原生及 managed 执行仍以 Read/PureCompute 为实际运行子集。D4.03/D4.04 必须补齐真实 StateEdit 的类型化执行适配、provider 接线和结果投影，不能仅将目录 eligible 改为 true。State 内不得 include Runtime 的 `detail/` 或访问裸 Handler。[S6]

独立 StateEdit 经同一 Operation 定义及当前 Policy 进入；满足 inline-safe 和线程条件时可使用 Native 完整调用，否则走已有 owning Submit。Atomic 复用受限调用适配而不是反复调用“会各自提交”的普通 StateEdit。长准备过程不能被放到 IPC/GUI/control 线程，域串行只承担短提交，不运行任意业务函数。

### 2.3 B5 到 B6 必查的结果与完成边界

B5 的 `execution_accepted` 与 `business_entered` 继续分别表达；取消/失败不能凭请求字段伪造。B5 为 Read/PureCompute 设计的 `outcome_read`、`outcome_failure`、`complete_read`、最小失败回执和 `read.finalization` 记录用途，不得未经检查直接推广为 State 的提交语义。[S7]

D4.03 为 State 路径准备、保存和验证 CommitFact/PublishedFact、PublicationProof 及结果 owner。D4.04 将它们接到现有 ExecutionSummary、get/wait/result.read 和必要收尾机制，不建第二执行表或 State 专属通知系统。摘要仍有界，组内步骤值由组结果预算负责，不为每一步伪造一次 Commit。

**不得为复用 B5 的失败兜底而丢掉已发布状态。** State 的 R、最小回执和必要发布材料必须在提交前验证并预留；Published 后的编码、普通日志、观察或额外记录错误保留原 CommitId/revision/应用事实，不改报 Rejected、FailedBeforeApply 或 CancelledBeforeApply。

## 3. D4.01：状态域与结构共享 Snapshot

### 3.1 数据与寿命

一个 domain 维护单个拥有型 `PublishedState{revision, immutable_root, history_cursor, lifecycle_generation}`。SnapshotHandle 拥有这一整份发布记录；不能分别加载 root、revision 和 History cursor 再拼成快照。根内正文、反向引用和必要索引也属于同一版本的不可变材料。[S2]

轻量配置 provider 使用类型化不可变 struct；通用对象 provider 使用私有结构共享容器。二者实现同一 provider 提交合同，不要求配置服务为了几个字段建立通用 Document、JSON 树或数据库。通用对象正文同样为受审类型化值，不把每个节点包装成动态 Payload。

快照读取不深复制全部对象、不取得长期阻止提交的资源写锁。旧 Snapshot 可继续安全读取它已取得的不可变版本，但不因此保留新写入权限。关闭/重开后，以旧 lifecycle generation 创建编辑或提交必须拒绝；域稳定 ID、对象身份、revision 与代数不得回绕复用。新读取与新编辑仍执行当前授权。

`shared_ptr<const T>` 本身不能证明不存在其他可变别名。本批须在输入冻结边界验证 owning 合同，或对必要可变容器做边界复制；Builder/EditView/可变根别名不得在发布后继续修改正式状态。共享不可变子树与错误地共享可变对象要有分别的正反例。

### 3.2 实施与完成条件

先完成独立配置根和 Snapshot，再接通通用对象根；不要用配置根的常数规模测试冒充大型对象表的结构共享验证。公开只读 handle 的模板和布局不得泄漏 immer 类型、allocator 或 mutable root 地址。

直接验证：无 Workspace/Document/SQLite/JSON 的消费者真实取得 Snapshot；多读者与提交交错只见完整旧版或新版；旧快照读值不变；可变别名写入不能污染已发布值；旧代数编辑拒绝；受持有快照保护的旧根安全保活，最后释放在关键锁外。

D4.01 正式完成必须包含通用对象根的实际行为，而不只是端口和轻量配置样例。后续索引更新和提交验证可在同批完成后归入对应逻辑用例。

## 4. D4.02：受限编辑、约束与内存 History

### 4.1 编辑能力

EditSession 持有 base Snapshot、WriteSet 与受影响约束集合。EditView 只暴露候选上的创建、替换、删除和查询；无 commit/rollback、裸 SQL、通用服务定位器或外部发送能力。CandidateReadPort 是只读候选视图，不能通过普通活动状态 Reader 偷换 read-your-writes。[S2][S5]

同一 EditSession 的变更串行执行。新增候选对象在组内使用稳定身份；失败后这些对象不进入正式目录。返回的业务值不得携带可继续修改候选的别名。只读查询本身不创建 History。

WriteSet 记录真实差量、前后对象/引用及受影响索引。容器层更新 k 项不得退化为复制 N 项；全局业务约束需要全量检查时单列其实际成本，不用缓存跳过约束。反向引用、对象差量与派生索引在同一 PreparedPublication 中准备。

### 4.2 约束与 History

删除被引用对象时，只能按已声明规则拒绝、显式更新引用或执行明确的受预算级联；不能静默留下悬空引用。校验必须基于完整候选视图，覆盖新增、删除、替换及跨对象约束；约束失败不污染正式 root、History 或已提交事件。

首版冲突粒度为域级 revision，不做自动 merge。保留 read/write sets 不代表已经提供细粒度冲突消解。独立 StateEdit 使用操作声明的 ServerCapture 或 RequireExplicitRevision；Atomic 完成绑定后必须有精确 revision 前置条件。[S2]

成功 StateEdit 即使有效 delta 为空，仍形成受治理的 commit 并推进 revision；不得优化为“没有变化所以直接成功”。正常 Atomic 编辑组只有一个 History 单元。Undo/Redo 是新的提交，revision 继续增长，不把旧 root 的 revision 直接还原；要求 Undo 的组必须全部具备有效逆向材料。超出保留窗口或不可撤销要明确报告，不能承诺无限历史。[S2]

### 4.3 实施与完成条件

先验证候选 CRUD/read-your-writes 和约束，再准备正逆差量与 History cursor。D4.03 可用后，通过真实协调器验证空 delta、Undo/Redo 与失败不发布；D4.02 不自建简化提交函数绕过许可。

必须有“改引用后删对象”“组中先建后引用”“删除仍被引用对象失败”“逆向材料不完整拒绝 Undo”“历史/快照 pin 下回收”“revision 上限拒绝”反例。大对象和旧根析构可以重入，因此先提交本地清理状态并保活 owner，锁外实际析构，不能释放后继续访问 this。

## 5. D4.03：内存 CommitCoordinator 与发布 gate

### 5.1 准备、许可、发布的唯一顺序

```text
输入/当前权限/目标/基准版本检查
    → 准备候选、约束、R、History 与必要回执容量
    → ReadyToCommit
    → 取得同域逻辑 CommitReservation
    → 最终核对 base revision / lifecycle / 完整许可绑定
    → CommitClaimed（一次性 consume 赢得仲裁）
    → Published（一次替换 PublishedState）
    → 必要记录、回调和 owner 收尾
    → Finalized / Execution Terminal
```

本批是内存后端，不产生 DurableCommitted，不实现 DB writer。CommitClaimed 不是成功，Published 才是内存正式状态可见点。Preparing 与 ReadyToCommit 失败不安装候选；已明确没有发布才能形成未应用失败。域 reservation 的寿命跨越许可与发布，但不是一直持有 mutex。[S2]

提交前准备所有可能失败或执行用户逻辑的材料：R 验证、差量/索引/History、结果与最小回执存储、可靠完成容量及发布证明所需存储。不能在 consume 后重新运行任意长业务验证、重算候选或首次扩容。预留证明存储不等于提前发放可验证为 Published 的 PublicationProof。

提交后用已验证材料与真实发布事实完成结果封装，避免再次运行可抛出的任意 R 验证器。若现有 Outcome/PreparedCommit 接口不足，只补受信的最小准备/封口协议，不能增加公开 skip-validation 或“传入已验证=true”的后门；相关变更同步合同和证明反例。

### 5.2 三个必须在实现中可定位的仲裁点

| 仲裁 | 唯一判据与允许结果 |
|---|---|
| 基准版本与同域并发提交 | reservation 下复核 base revision；同一 base 的两个候选不能都覆盖成功。一个发布后，另一个明确冲突，不自动重算 |
| cancel/revoke/deadline/close 与 CommitClaimed | 当前许可消费必须与撤权/取消及生命周期失效确定唯一先后。先失败不发布；claim 先赢则后到请求不能抹掉该提交尝试的最终事实 |
| Published 与读者/查询/事件 | 一次拥有型 PublishedState 替换；只有对应发布证明有效后，查询和业务成功事件才能报告已应用 |

不能写成 `if (!cancelled) { consume(); publish(); }` 的三个无关检查，也不能在两把独立锁下先读生命周期、再消费一个早已失效的 permit。State 通过已配置的可信 authority 获取/消费许可，expected binding 从当前受信上下文构造，不能从传入 permit 反取 expected。[S2][S5]

**本批实施决定：** 用同域逻辑 reservation 阻止其他发布和破坏性关闭，外部 authority 调用在内部 mutex 外进行；关闭/代数改变与 action 消费通过同一受信仲裁协议接线。close 先赢使未 claim 候选失效；claim 先赢则关闭进入 draining，保留 reservation/依赖直到发布或已确认失败。不得在 claim 后再凭普通 closing 标志把确定提交改成未执行。跨组件协议无法由现有端口表达时，补窄协议并形成一次 ADR；不将 Runtime::Policy 私有对象泄漏给 State。

### 5.3 inline、重复、迟到和异常

调用 provider 的 begin/prepare/commit 以及 receiver/observer 都是潜在重入边界。协调器先发布可被回调引用的状态并持有本地 owner，解锁后调用；回调可早于 commit() 返回。返回路径不得假设仍 Pending，更不得用后到的返回错误回滚已经收到并核验的 Published 事实。

接收回报逐项核对 provider/domain、CommitId、ReservationId、base revision 与 lifecycle generation。相同尝试完成只认一次；重复回报不得双发事件、双增 revision 或双释放。旧代数/旧 reservation 的迟到回调不得替换新根。合法后端拒绝后的所有权与回调排空规则必须明确；违约后端仅用于防御反例，不认证为支持后端。

内存发布路径应在材料已准备后执行无业务回调、无必要扩容的短交换。若发布后才发现不可恢复内部不变量破坏，保留已发生事实并隔离/终止，不能声称回滚。普通观察或日志失败不改变成功提交；必要记录失败沿 A05 的事实/封锁/排空规则处理，不通过 detach 伪造停止成功。[S2][S8]

### 5.4 结果与停止

StateCommitted 必须与唯一真实 CommitFact、PublishedFact、domain、revision、published_version 和有效 PublicationProof 一致；只含 CommitId 的 DTO、已发放 permit 或 PreparedCommit 不能通过证明校验。取消先赢且可证明未应用才是 CancelledBeforeApply。

StateEdit 的输出验证/预算错误尽量在 commit 前拒绝；Published 后即使某个协议消费者无法编码完整 R，也保留可查询的提交事实和已准备结果，不套用 B5 的 Read 失败兜底。RPC 发送失败不回滚状态；外部结果和事件投影服从同一 publication gate。

Host StopAccepting 不等于销毁 domain。已有合法 admission 的提交按其策略完成或取消；停止超时报告未 quiescent，并继续持有编辑、reservation、回调、根和代码 owner。Snapshot 的纯不可变保活与仍在执行的回调分别计量；旧快照不是允许重新编辑已关闭域的凭证。

## 6. D4.04：独立 StateEdit 与 Atomic 同源绑定

### 6.1 一份业务函数，两种协调入口

```text
独立 StateEdit：一个 EditSession → 同一 state_edit 函数 → prepare → 一次 commit
Atomic 编辑组： 一个 EditSession → 顺序调用同源步骤 → prepare → 一次 commit
```

不复制业务 Handler，不循环调用每次都会提交的普通命令，不为组内步骤逐个创建 ExecutionRef。外层需要异步时复用 B5 的 Execution owner；组内只允许完整执行的 StateEdit、CandidateRead、PureCompute。[S2]

本批入口为类型化、有限的 Atomic 组描述/执行适配，供原生消费者与后续 B7 编译器复用。它不是新的 Plan IR、DSL 或独立 JSON 解释器。`call/let/assert` 的原子子集语义沿用 A07/A08；完整 wire 解析、slots 编译与 PlanRunner 仍在 B7。不得因为不做 PlanCompiler 而遗漏原子候选步骤、断言和组级结果的实际验证。[S2][S3]

### 6.2 预检与逐步检查

组开始前确定唯一 provider/domain、精确 revision、操作精确版本/契约、步骤资格、完整目标边界及额外独占资源集合，并一次申请全部必要外部资源。不允许执行到中间才根据结果取得新的外部锁域；不能预先确定的组合明确拒绝。组内新对象属于既定域候选，不产生新的外部资源域。

每一步仍检查实际参数、目标、类型和当前权限；预检不是无限有效的许可。组的最终 ActionPermit 绑定实际操作/组摘要、目标范围、权限与生命周期世代、期限，并覆盖全部需要授权的编辑，不能仅用最后一步或其中一个高权限步骤的许可代表全组。

普通 Read 默认不进入 Atomic；需要候选读取时用已注册 CandidateReadPort。PureCompute 只能读取不可变输入或候选已有值，不读取漂移活动状态。所有步骤共享同一候选视图，并按定义顺序运行，不允许同一 EditView 并发使用。

### 6.3 严格拒绝与输出边界

拒绝跨 provider/domain、Effect、Lifecycle、ticket、await、嵌套 Atomic、if/foreach/parallel，以及需要外部等待或异步派发的步骤。SDK 若展开固定小循环，展开后步骤和内存预算照常计算，不把控制流偷偷留进组内。[S2]

任一步失败或提交前取消，正式 root、History 与已提交事件均不出现部分修改；候选值不得作为正式结果从 get/result.read/Notification 导出。成功后才返回组值和 commit 材料，正常原子编辑组只产生一次 revision 推进、一个 History 单元和一个组级回执。组级回执不是声称已实现跨进程或持久幂等引擎。

组级 Undo 要求全部编辑可逆；逆向材料失败在正式发布前拒绝。有效空 delta 按 A05 仍执行一次受治理提交。普通不进入 Atomic 的纯读/计算仍不制造 History。

### 6.4 与外部协议的边界

本批必须完成安装后类型化 Native/managed StateEdit 与 Atomic 闭环，不要求提前实现 B7 的 `plan.check/submit`。现行 A17.2 要求修改 RPC 带 IntentKey；不得为了展示 B6 新增一个绕开该规则的无意图写入口。需要扩展既有动态 StateEdit 入口时，必须同时落实现行意图/能力规则和同源验证；未具备的入口保持不暴露或明确拒绝，不伪造可重试/去重能力。[S8]

## 7. 构建组合、依赖与 SDK 交付

当前 `OCK::State` 是 ContractBaseline，占位创建还位于动态组合分支。B6 须将 State 提升为真实生产静态库，并使它能在没有 Data/Asio 的独立配置下构建。只修改 target link 而仍强制获取 jsoncons/CLI 不算完成裁剪。[S9]

### 7.1 本批拟新增的构建选择

以下名称是本规划的实施决定，**当前 CMake 尚未提供**；它们是构建选择，不增加架构正式产品 Profile。

| 构建选择 | 组件与依赖取得要求 | 安装/消费验证 |
|---|---|---|
| `Runtime`（保留） | Runtime/CoreContracts/Foundation；不取得 immer/thread_pool/动态库 | 无 State 的原生短调用真实运行；请求未安装 State 明确失败 |
| `Embedded`（保留） | 原 Runtime + CpuPool；仍只取 expected/thread_pool | 原完整任务/资源/取消与占用边界保持；不自动拉入 State |
| `StateNative`（新增） | Runtime + State；取得 expected 与锁定 immer；不强制 CpuPool/Data/Asio/数据库 | 无文档 settings_service 独立构建、安装、取快照和提交 |
| `B6Subset`（新增） | 累计 B5 可用组件 + State；在既有 CLI/CpuPool 依赖取得上增加 State 所需依赖 | Native/managed StateEdit、Atomic 与既有结果协议相关消费者 |

具体依赖组件参数以现有依赖取得工具为准，在实现中同步映射，不在本规划伪造一条已经可执行的命令。通用对象 provider 继续使用锁文件中的 `immer v0.8.1 / 5875f7739a6c642ad58cbedadb509c86d421217e`；本批不升级锁定依赖。[S10]

State 对外仅导出 CoreContracts 依赖。immer 只参与 State 实现编译，安装公共头不要求消费者 include immer；如果类型化轻量根需要公开模板，模板不得泄漏通用对象容器后端。StateNative 中不启动隐式文件日志、后台 GC 或每域线程；需要排队/续体时复用受管执行资源，不能按域数量无限增线程。

SDK 版本、`OCK_IMPLEMENTATION_STAGE`、已实现组件清单、安装头/签名摘要与 missing-component 探针按实际变更同步。下一开发版本可采用 `0.1.0-dev.7`，这是本批建议而非当前发布事实；不宣称既有严格消费者对新增字段/接口无修改兼容。未实现的 Automation/Durable 等保持不可用，不能因累计构建选择名为 B6 就改为 Implemented。

## 8. 预算、回收与性能要求

### 8.1 继承的硬规则与本批配置责任

Atomic 步数最多 128；候选 delta 与新增分配采用现行 64 MiB 上限；名称/slot 遵循各自现有长度与格式合同。共享已有快照另计 pin，不能每次全额重复计费，也不能不计保活成本。内存模式不放宽权限、取消、History 或实际目标验证。[S11]

StateOptions 至少明确 domain/编辑/在途提交数量、候选与结果拥有字节、History 保留条数及字节、Snapshot/History pin、回收批量。架构未给出数值的项不在本文伪称为已批准默认；实施时由可信组合配置显式给出正的有限值，并在正式 expected 与容量测试前固定。请求方只能收紧预算，不能自行扩大。

借鉴 B5 收口：活动额度、普通可回收缓存与受保护 pin 分账；硬准入压力能够驱动有限回收，而不是只有永远达不到的软阈值才回收。全 pin 时明确拒绝，释放后可恢复；不能以扩大限额、删除必要 History 或丢失提交回执来掩盖长期运行问题。新增幂等/恢复所需的保留责任不能混进普通终态淘汰。[S1]

**输入、候选、结果与旧根分别按实际 owner 寿命计费。** State 提交后候选可能转成正式根，不能照搬 B5 settled input 的释放点归还仍被 PublishedState/History/结果引用的数据预算。回收先拆索引、再锁外销毁；释放失败或在途 callback 不得虚减实际使用量。

### 8.2 必测成本与低风险优化

通用对象根按 1k/10k/100k 对象、修改 1/10/100 项记录 Snapshot 获取、准备、提交和回收的延迟、分配/复制量；约束全扫单列。容量不支持的组合明确拒绝并记录，不能静默缩小后报通过。准备成本与短发布成本分开，保存原始样本，不预先编造吞吐或 P99 承诺。[S11]

优先采用已有结构共享、只更新受影响反向引用、注册期复用不可变契约材料、锁外析构和短发布；不引入第二缓存真相、无锁框架或新的线程模型。Snapshot 获取不应随 N 线性复制；k 项更新不因容器实现复制全部 N 项。

B6 State 组合占用单列，不把新增状态成本塞入无 State 的 Embedded 原预算。若 Runtime/CoreContracts 热路径或装配改变，按 A21 复测受影响 Native/Embedded 的实际链接、Ready、线程、受限 Invoke 分配和回收；不机械重跑全部历史 G3，也不以“到 G4 再测”跳过受影响指标。State 的绝对性能数值由真实样本与受审配置建立，不用本轮结果自动加余量抬门槛。

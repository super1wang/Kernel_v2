## 3. F1｜取消、关闭与 CommitClaimed 未同源仲裁
P1 · 责任：Runtime Invocation / Policy 桥接 / StateDomain

### 源码事实

NativeBound::run 的 StateEdit 路径先 prepare Action、issue permit，再进入 provider/业务。validate_state_request 只在前面检查 stop_requested；所读调用链没有把 WorkContext 的 stop token 转接至该 ActionAuthorization::cancel。ActionAuthorization::consume 只查询其自身 action 状态、权限、期限与绑定，不读取这份 WorkContext stop。[S07–S09]

StateDomain::commit 先在域锁内置 phase_=Claiming，再解锁调用 authority.consume。此时 close() 只设置 close_requested 并返回，即使 consume 尚未获得其真实仲裁。memory_commit.cpp 还在假 authority 的 consume 回调中先 close、随后才返回消费成功，并期待发布成功；这个用例不能证明原计划的“close 先赢即拒绝”。[S05、S14]

### 必须增加的交错

```text
A：StateEdit 已 Started，业务暂停在提交前
B：请求取消；stop token 已置位，尚无 CommitClaimed
A：业务正常返回 → prepare → consume → publish
当前链路：取消状态未进入 Action 仲裁，仍可能发布
```

这里不是要求强制中断 C++ 业务。允许 Started 后业务协作运行，但正式提交仍须遵守取消与许可消费的先后。Scheduler 的 Started/AlreadyClaimed 与 State 的 CommitClaimed 是不同决定点，不能互相替代。[S03]

### 最终修复要求 C1

建立本次编辑的 owning commit-action 控制对象，把取消、期限、撤权以及域关闭的失效请求汇入同一个可信消费协议。stop relay 在任何可能同步回调前完成安装；已 requested 的 token 也必须生效。close 在消费未赢时使本次提交不可消费；消费先赢则 close 等实际发布或确定失败，不撤销事实。

域锁外调用 authority，但不能仅用“准备调用 consume”的布尔位冒充消费成功。若现有 CoreContracts 不足，补一个窄的跨组件仲裁接点并同步 ADR；State 不引用 Runtime 私有 Policy。取消回调与 cleanup 的 owner 都必须保活，回调析构不得在其可能等待的锁内进行。

验收：真实 Policy＋Host 提交，分别强制 cancel/revoke/deadline/close 在消费前和消费后；前者无 root/history/CommitFact，后者保留唯一实际提交。修正假 authority 旧断言，不能只追加一条普通 Policy 单测。


## 4. F2｜发布证明缓存会被后续提交覆盖
P1 · 责任：ObjectMemoryProvider / StateEdit 结果封口

### 源码事实

ObjectMemoryProvider::commit_inline 完成后清空 owned_、设置 committing_=false，并把结果写入单个 optional published_。Runtime state_edit_native 在 commit_inline 返回之后才调用 publication->attest(本次 CommitId)。该 attest 只接受 published_ 中最后一次提交；失败随后触发 invariant，封口异常会 terminate。[S06、S08]

```text
线程 A：commit_inline(C1) → Published，释放 committing
线程 B：begin/prepare/commit_inline(C2) → 覆盖 published_
线程 A：attest(C1) → InvalidProof → invariant / terminate
```

单域最多一个在途 reservation 不能排除此时序：A 已完成提交并放开 provider，结果封口尚未结束。多个合法 session/binding 可以形成以上交错。直接顺序调用“提交 C1、提交 C2、再索取 C1 证明”也能核对缓存行为；本轮未运行该新增复现。

### 最终修复要求 C2

把 PublishedCommit、真实 PublicationProof 与已准备业务结果绑定到同一个提交尝试的 owning completion 材料。调用者消费该材料完成 Outcome 封口，不依赖 provider 的 latest publication 槽。优先从 commit 完成结果交付逐次证明；如采用受限查询保存，必须有明确 pin、上限、回收与完整 identity，不做无限证明缓存。

保留身份校验：provider/domain、CommitId、ReservationId、base revision、lifecycle generation 及当前尝试 owner。commit 返回报告先核对完整 PreparedIdentity 与合法 disposition，再进行结果组装；不能只看到 Published 枚举就接受。闭环必须适用于 Native 及 managed 两条路。

不能以删除 invariant、把失败改成普通 FailedBeforeApply、扩大域锁范围到业务/回调，或只保证“通常来不及并发”解决。Published 后已应用事实必须保留；证明在本次合法封口完成前不能被下一次提交或普通 History 淘汰使其失效。

### 验证

用屏障固定 C1 Published→C2 Published→C1 封口；两次结果都能得到对应事实且进程存活。补回调早于返回、返回错误晚于已核验 Published、错 reservation/commit/domain、History 压力和 close/reopen 组合。新阶段仍须按既定代数规则拒绝旧编辑，不能借此放宽新写入权限。


## 5. F3 / F4｜生命周期同步与 reservation 恢复
P1 数据竞争；P2 可恢复失败后的可用性

### F3：identity_ 不是线程安全发布对象

StateDomain::reopen 在域 mutex 内替换普通 shared_ptr identity_。snapshot 只在锁内捕获 current_，随后在锁外读取 identity_；validate 与 commit 的证明创建也读取 identity_ 而未使用同一同步边界。并发 reopen 与这些读访问的是同一个 shared_ptr 成员，不是各线程的独立副本。[S05]

这既有共享成员的数据竞争，也可能拼出“旧 PublishedState＋新 identity”的混合材料。现有测试仅串行重开；一写一读的普通 publish 测试不写 identity_，因此不能覆盖此问题。[S14]

C3 要求：在同一域仲裁内捕获 PublishedState 和其 identity/generation，所有校验基于这一一致快照；或原子发布一个包含两者的不可变整体。validate 和证明创建遵循相同协议。不得只把一个字段换成原子而继续拼装不同世代。

### F4：prepare 成功后缺少唯一的放弃/失败清理

prepare 会将 PreparedState 强持有在 domain.active_。commit 在 target/lifecycle 参数检查失败或 Proof 分配 bad_alloc 时直接返回，未进入 finish_failed。ObjectMemoryProvider 随后清空自己的 owned_，但 domain.active_ 仍占用；后续 prepare 可一直 Busy。直接丢弃 prepare 返回的句柄也不会移除 domain 的强 reservation，且没有匹配的 abort 接口。[S05、S06]

修复不能“每次错误都清空 active_”：错误或伪造请求不得撤销另一尝试的候选。应提供按真实 owner＋完整 identity 验证的一次性取消准备材料路径，或等效 RAII prepared lease。ClaimWon 前可放弃；之后由提交完成 owner 排空，不能借取消释放正在使用的材料。

### C3 的统一寿命要求

把准备、消费、完成、关闭涉及的 owner 移出成员后再进入外部调用；公开 StateDomain 方法跨 authority/用户正文析构应局部保活自身。所有早退、可恢复分配失败、放弃与异常归还本尝试额度一次。不得用 close/reopen、扩大 inflight 或忽略 Busy 当恢复机制。

验收：并发 snapshot/validate/commit 与 close/reopen；证明分配故障后立即重试；prepare 后主动放弃；错误/伪造句柄不影响合法在途候选；外部回调删除当前外壳仍安全。采用受控屏障与 ASan；ASan 不替代对共享成员同步的代码证明。


## 6. F5｜Atomic 只复用了函数，尚未复用完整治理
P1 输入合同缺失；D4.04 生产接线遗漏

### 可直接定位的输入差异

AtomicStep::state_edit/candidate_read/pure_compute 使用 FrozenRoot<A>::freeze 保存输入，但 FrozenRoot 只执行 RootContract 的 freeze/bytes，没有 TypeContract<A>::validate。三种 step 的闭包随后直接调用传入函数。ObjectValue::freeze 会验证输出，因此这里是输入缺口，不能误写为所有验证都缺失。[S10、S11]

```text
现有 Command 合同：id 为空 → TypeContract 拒绝
RootContract<Command>::freeze：直接返回原值
Atomic：合法 edit ＋ id 为空的 pure_compute step
若描述授权通过，输入可能进入业务；Native 会先拒绝
```

atomic_group.cpp 具备上述 Command 类型和 compute 函数，但未构造这个反例。单独运行纯计算组最终会被拒绝，复现时必须包含合法 StateEdit；不能用那个组级拒绝掩盖输入校验缺失。[S15]

### 不是 Registry 同源绑定的替代品

当前 step 接收调用方拼出的 AtomicDescription、OperationKey/digest 和裸函数指针；没有验证这些描述与实际冻结注册项的对应关系。authorize 只拿描述和 WorkContext，无法核验本次 Args 的真实目标投影；resources 仅作为 ObjectId 列表传给 preflight，没有生产 MultiClaim/owning Lease 接线。测试 authority 还明确拒绝一切非空资源列表。[S10、S15]

这不证明恶意 native 模块被安全隔离绕过——该隔离从来不是目标。缺的是面向正常上层消费者的受治理生产入口：同一注册身份、参数与目标校验、完整组授权、实际资源和执行寿命。

### 最终修复要求 C4

由 Runtime/组合层从冻结 Registry 产生有限的候选调用适配，持有真实 handler/类型/provider/code owner；State 仅消费 CoreContracts 窄调用端口。绑定来自真实操作，描述不能替换实现。统一输入归一化/TypeContract、实际目标投影、逐步当前权限、整组 permit membership 与一次 MultiClaim；运行 owner 持有 Lease 至组实际排空。

完成类型化 Native/managed Atomic、候选 assert 及必要的有限值绑定/组结果验证，不实现第二 Plan IR。若保留裸指针构造器，只作为明确受信内部/测试装配，不把它作为完成 Registry parity 的证据。公开写 RPC 未具备 Intent 责任时仍不暴露。


## 7. F6｜History 与预算的持续运行边界
P2 · 必须修复压力恢复；能力扩展不得伪称原要求

### 字节先满、环未绕回时可永久拒绝新提交

prepare 只从 history_bytes_ 中减去“本次将覆盖的那一槽”，不尝试回收其他可淘汰记录。设 history_entries=8，每条计费为 H，history_bytes=2H：两次提交后第三次要写的槽为空，2H+H 超限，提交被拒绝。没有外部 pin 也不会主动回收旧槽；reclaim_batch 只用于 reopen 清理循环，不是正常准入压力回收。[S05]

这个反例是配置推导，H 须按测试中真实 sizeof(HistoryRecord<T>)+delta_bytes 计算；不得硬编码跨工具链的 sizeof。本次未运行该新增用例。

### 预算与实际 owner 需统一说明

HistoryRecord 保存 before/after FrozenRoot 和 delta_bytes 标量，未持有 ObjectEdit 的 ObjectChange 序列。环外 HistoryView 仍可保活被替换记录，当前 history_bytes_ 只统计环内项。ObjectRoot::owned_bytes 主要累计正文/引用列表，未包含实际 immer 对象索引和反向索引节点分配；它不能直接当完整堆占用或新增分配计量。[S05、S11–S13]

保存结构共享根本身并非错误，也不必强行改成深复制差量。问题是文档声称的差量/拥有预算与可证明范围不同。应明确逻辑引用量、唯一共享节点占用、实际新增分配和 ring 保留量四个口径，不凭一个 delta_bytes 数字证明全部容量约束。

### Undo/Redo 的实际能力

prepare_undo 只看最新记录且拒绝 latest.kind==Undo；当前测试明确断言第二次 Undo 失败。由此只能宣称单次 Undo/Redo 切换。原规划没有写死可连续撤销次数；多级 Undo 是本报告建议明确的能力选择，不把它伪称成已给定数量的旧要求。[S05、S13、S14]

### 最终修复要求 C5

为普通可回收 History 建立有限的准入压力扫描，保护当前状态、外部 Snapshot/History/结果/在途引用；全 pin 时有界拒绝，释放后恢复。独立跟踪环内索引与实际 owner 计费，算术预检并覆盖加法溢出。准备候选和共享节点的分配预算应在可信边界约束，失败不改变候选或正式根。

## 9. 低风险、高收益的优化建议
先修正确性；性能数字由同语义测量决定

| 优先级 | 建议 | 收益与约束 |
| --- | --- | --- |
| 随 C2 必做 | 逐提交交付 publication proof，避免 latest 查询 | 同时消除竞态、少一次查找；不能换成无限缓存 |
| 随 C5 必做 | 预算分账与压力回收 | 恢复持续运行能力；不靠扩大上限或错误丢 pin |
| 正确性后 O1 | 复用已经冻结/验证的同一候选材料 | edit.freeze→domain.prepare 再 freeze 会重复全量引用验证；仅在可信不可变证明覆盖时消除重复 |
| 测量后 O2 | WriteSet 提供有界 key→index 索引 | 当前每次 update 线性查 changes；大 k 时可减少重复查找，保持小表低成本 |
| 测量后 O3 | 准备阶段轻量 reservation / 预算先行 | 减少已经 Busy 时仍冻结、分配整份候选与 History 的浪费；不把业务放进域锁 |
| 工程质量 O4 | 可信端口合同与样例分层 | 生产公开 Host 样例与内部单测分开命名；测试 mock 不冒充已支持后端 |

ObjectEdit::begin、ObjectEdit::freeze 与 StateDomain::prepare 的对象根冻结都可能调用 validate_references；存在大表重复遍历机会。删除重复检查前必须证明中间根不可变且所有必要约束已覆盖，并保留故意破坏引用/非法输入的反例。[S05、S11、S12]

不要为缩短锁而把权限、版本或一次性消费检查移出共同仲裁；不要为降低计数删除目标投影或复用已过期授权。性能回归应分别记录准备成本、短发布时间、锁等待、分配字节、被保活旧根，而不是只记录总耗时。

### 本轮明确不做

不重写 Scheduler、线程池或共享 IOCP；不重选 immer/jsoncons；不加入全局缓存真相、数据库或第二解释器。之前 IPC 二次复制、协议 Schema 每连接构建等优化可独立排队，但不是本轮闭合 State 正确性的前置。

本轮没有新增实测性能结果，不给加速百分比。新方案优先收益是消除错误状态、崩溃时序与长期拒绝，性能优化使用 C6 的真实成本矩阵确认。

## 11. 接口与所有权必须冻结的七条规则
供实现者逐条自检；不是未经编译的替换代码

| 规则 | 不可退让的语义 |
| --- | --- |
| K1 开始与提交 | Executor Started、执行取消意图、Action CommitClaimed、Published、Terminal 分开；每种状态都有唯一 owner |
| K2 提交许可 | cancel/revoke/deadline/close 失效与 consume 使用可信共同仲裁；域锁外调用 authority 但不提前认定消费成功 |
| K3 准备材料 | 真实 PreparedState owner＋完整身份配对；只有本尝试可放弃，ClaimWon 后不能随意释放 |
| K4 发布结果 | 每次提交自己的证明/事实/结果拥有至封口与必要回调排空；latest 缓存不承担可靠完成 |
| K5 代数 | PublishedState 与 proof identity/generation 一致捕获；旧 Snapshot 可读旧数据但不能新写 |
| K6 组治理 | step 实现、签名、provider 与权威注册身份绑定；实际参数/目标每次验证；资源一次全取 |
| K7 计费 | 候选转为正式根不是释放；索引摘除不是 owner 销毁；pin、共享节点和实际新增内存各有口径 |

### 建议的状态流

```text
Prepared owner（候选/结果/最小回执已预留）
  ├─ 取消/关闭/失败赢 → Exact abandon → 锁外实际析构
  └─ 可信 consume 赢 → CommitClaimed
                       → 单次 PublishedState 替换
                       → 本次 proof + report + result 封口
                       → 必要回调 / child / owner 排空
                       → Terminal
```

不能为本次内存后端加入伪 DurableCommitted；不能在结果封口失败时重新运行已提交业务。State 的成功结果和失败事实继续进入唯一 Execution 表与已有观察投影，普通日志/通知失败不改变应用事实。

### 并发测试的执行约束

用 latch/barrier/受控端口固定窗口，不以 sleep 运气或 repeated-until-pass 作为证明。故障端口只用于测试，不把能跳过 Policy 或任意设置 Published 的开关带入产品。对每次临界交错同时断言 root/revision、History、事实、回调数、reservation/Lease 与结果 owner。
